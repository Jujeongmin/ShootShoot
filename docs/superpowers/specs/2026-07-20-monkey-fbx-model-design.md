# 원숭이 FBX 모델 교체 (설계 문서)

- **날짜**: 2026-07-20
- **선행 작업**: [2026-07-16-shootshoot-monkey-sniper-design.md](2026-07-16-shootshoot-monkey-sniper-design.md) — 이 문서의 "프리미티브로 조립된 원숭이" 부분을 대체한다.

## 1. 목표

지금까지 `game/src/gameplay/monkey.js`는 Three.js 프리미티브(캡슐/구/원/튜브)로 원숭이를 조립해서 만들었다. 사용자가 실제 3D 모델 에셋(`monkey.FBX` + 텍스처 + 애니메이션)을 제공했으므로, 이를 로드해서 프리미티브 조립 방식을 완전히 대체한다. 게임의 나머지 부분(레이캐스트 판정, 점수, 라운드 진행, `targetManager`)은 `createMonkey()`의 반환 인터페이스가 그대로 유지되는 한 변경 없이 동작해야 한다.

**성공 기준**: 원숭이가 실제 3D 모델(텍스처 입혀진 상태)로 렌더링되고, 내장 애니메이션이 재생되며, 기존 사격/점수/라운드 로직이 그대로 작동한다.

## 2. 에셋

- 위치: `game/public/textures/Monkey_animated/`
  - `monkey.FBX` — 바이너리 FBX(v7400), 애니메이션 클립 포함(추정, 로드 후 확인 필요)
  - `body_u1_v1.png`, `body_u2_v1.png` — 몸통 디퓨즈 텍스처 2종
  - `head_u1_v1.png` — 머리 디퓨즈 텍스처
  - `eyes_u2_v1.png` — 눈 텍스처
  - `NormalMap.png`, `NormalMap2.png`, `NormalMap3.png` — 각각 body_u1/body_u2/head에 대응하는 노멀맵(추정)
- **`game/public/textures/Monkey/`(정적 버전, 애니메이션 없음)는 중복이므로 구현 시작 시 삭제한다.**
- 이 에셋의 존재로, 기존 설계 문서의 전역 제약 "No external asset files"는 **원숭이 모델에 한해 무효화**된다. 나머지(오디오/기타 비주얼)는 기존 제약 유지.

## 3. 신규 의존성

- `fflate` (npm) — `THREE.FBXLoader`가 압축된 바이너리 FBX geometry를 파싱하는 데 필요. 현재 미설치.

## 4. 아키텍처

### 4.1 로딩 전략 — 한 번 로드, 인스턴스마다 복제

FBX 로딩은 비동기이고, 라운드마다 여러 마리(최대 10마리)가 스폰되므로 매번 새로 로드하면 안 된다.

- 게임 부트스트랩(`createGame()` 초기화, 메뉴가 뜨기 전)에서 **한 번만** `FBXLoader.loadAsync()`로 모델을, `TextureLoader`로 텍스처 7장을 로드해 캐시에 저장한다.
- 이후 `createMonkey()`가 호출될 때마다(라운드 스폰 시)는 캐시된 템플릿을 **복제(clone)**해서 사용한다.
- 로딩 UX: `createGame(container).start()` 호출 시, 로딩이 끝나기 전까지는 `screens`에 메뉴 대신 "로딩 중..." 텍스트만 표시하고, 로딩 프로미스가 resolve되면 그제서야 `screens.showMenu(startGame)`을 호출해 정상 메뉴로 전환한다. 별도의 프로그레스 바나 애니메이션은 만들지 않는다(비목표).

### 4.2 재질(Material) 독립 복제

three.js의 `Object3D.clone()`은 지오메트리/재질을 **참조 공유**한다. 원숭이별로 피격 시 개별적으로 페이드아웃해야 하므로, 복제 시 각 메쉬의 재질도 명시적으로 `.clone()`해서 완전히 독립적인 재질 인스턴스를 갖도록 한다. 텍스처(Texture 객체) 자체는 공유해도 무방하다(읽기 전용으로만 쓰이므로).

### 4.3 텍스처 매핑

FBX를 로드하면 내부에 여러 재질 슬롯이 있을 것으로 예상되나(body×2, head, eyes), 정확한 슬롯 이름은 사전에 알 수 없다(바이너리 FBX라 정적으로 확인 불가). **구현 시 실제로 로드해서 재질 이름/개수를 로그로 확인한 뒤**, 아래 매핑을 적용한다:

| 재질(추정) | 디퓨즈 | 노멀맵 |
|---|---|---|
| body variant 1 | `body_u1_v1.png` | `NormalMap.png` |
| body variant 2 | `body_u2_v1.png` | `NormalMap2.png` |
| head | `head_u1_v1.png` | `NormalMap3.png` |
| eyes | `eyes_u2_v1.png` | (없음) |

재질 이름이 이 표와 다르게 나올 경우, 실제 이름에 맞춰 매핑 코드를 조정한다(이름 리스트를 먼저 확인하고 나서 매핑 코드를 작성하는 순서로 구현).

### 4.4 애니메이션 — AnimationMixer

기존의 절차적 애니메이션(코드로 위치/회전을 매 프레임 계산)을 버리고, FBX에 내장된 애니메이션 클립을 `THREE.AnimationMixer`로 재생한다.

- 로드된 FBX의 `.animations` 배열(클립 목록)은 구현 시점에 실제로 로드해서 이름/개수를 확인한다. 클립이 여러 개면 이름으로 idle/타운트 등에 매칭을 시도하고, 하나뿐이면 그것을 기본 반복 재생으로 사용한다.
- 원숭이 인스턴스마다 독립된 `AnimationMixer`를 가져야 한다(믹서는 특정 스켈레톤 인스턴스에 종속적).
- `monkey.update(dt)`에서 매 프레임 `mixer.update(dt)` 호출.

### 4.5 피격 반응

내장 애니메이션과는 별개로, **기존의 넉백+회전+페이드 로직을 그대로 유지**하고 모델 전체(group)의 transform에 덧씌운다 — 믹서가 idle 애니메이션을 계속 재생하는 동안 group 자체가 뒤로 튕기며 회전하는 방식(둘은 서로 다른 레벨에서 동작하므로 충돌하지 않는다).

- 페이드아웃은 모델을 순회(`traverse`)하며 발견되는 모든 메쉬의 재질에 `transparent = true` + `opacity` 애니메이션을 적용한다(기존엔 재질 2개만 다뤘지만, 이제는 개수가 가변적이므로 순회 방식으로 일반화).

### 4.6 헤드샷(부위) 판정

FBX 내부 메쉬 이름을 알 수 없으므로, 명칭 기반 매칭 대신 **로컬 좌표 높이 기준**으로 부위를 판정한다:

- 로드 직후 모델의 바운딩박스를 계산한다.
- 레이캐스트로 명중한 지점의 로컬 y좌표가 바운딩박스 상위 일정 비율(예: 상위 25~30%) 안에 들면 `'head'`, 아니면 `'body'`로 분류한다.
- 정확한 비율은 실제 모델 형태를 보고 구현 중 튜닝한다(원숭이가 웅크린 자세인지 등에 따라 달라질 수 있음).
- 레이캐스트 대상 메쉬 목록(`getRaycastMeshes()`)은 모델을 순회해 찾은 모든 `Mesh`를 포함하고, 각 메쉬의 `userData`에는 `monkeyId`만 넣고(`part`는 넣지 않음), **명중 시점에** 교차점의 로컬 y좌표로 부위를 판정한다. 이는 기존 방식(메쉬별로 미리 `part`를 태깅)과 다른 지점이므로, `game.js`의 명중 판정 로직도 이에 맞춰 조정이 필요하다 — 정확한 히트 포인트를 얻기 위해 `raycaster.intersectObjects`의 결과에서 `intersection.point`(월드 좌표)를 모델의 로컬 좌표로 역변환해서 판정한다.

### 4.7 스케일/방향 보정

FBX는 내보낸 프로그램에 따라 단위(cm vs m)나 축 방향(Z-up vs Y-up)이 다를 수 있다. 로드 후 씬에 배치했을 때 크기나 방향이 기존 원숭이(약 1.5~2 유닛 높이, Y-up, 카메라를 정면으로 바라봄)와 맞지 않으면 `scale`/`rotation` 보정값을 적용한다. 정확한 값은 구현 중 실제로 렌더링해보고 눈으로 확인하며 조정한다(사전에 정확한 수치를 특정할 수 없음).

## 5. 인터페이스 (변경 없음)

`createMonkey({ id, position, scale, speed })`의 반환 형태는 기존과 동일하게 유지한다:
```
{ id, group, getRaycastMeshes(), update(dt), hit(part), isDead(), getWorldPosition(target?) }
```
`targetManager.js`, `game.js` 등 다른 모듈은 이 인터페이스에만 의존하므로 원칙적으로 수정이 필요 없다. 단, 4.6에서 설명한 대로 "명중 시점에 부위를 로컬 좌표로 판정"하는 방식으로 바뀌면서 `game.js`의 레이캐스트 처리 부분(`intersection.object.userData.part`를 바로 읽던 부분)은 손봐야 한다.

## 6. 비목표 (YAGNI)

- 애니메이션 클립을 세밀하게 여러 개(걷기/공격 등) 활용하는 것은 이번 범위 밖 — 사용 가능한 클립 중 적절한 것 1~2개(기본 반복용 하나, 있으면 도발용 하나)만 활용.
- 로딩 화면 폴리싱(프로그레스 바 등)은 만들지 않음 — 최소한의 "로딩 중" 표시만.
- LOD, 텍스처 압축/최적화는 하지 않음(사용자가 품질 우선을 선택함).

## 7. 열린 위험

- FBX 내부 재질 이름, 애니메이션 클립 이름/개수, 정확한 스케일/방향 보정값은 모두 구현 중 실제 로드 후 확인 필요 — 사전에 정확히 명시 불가능한 항목들이다.
- 텍스처 총 용량(노멀맵 3장 포함 약 10MB)으로 인해 초기 로딩이 느릴 수 있음(품질 우선으로 사용자가 확인함).
