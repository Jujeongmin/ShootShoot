# 라운드 진행 설계 — 골드 배율과 다채로운 판

라운드가 올라가도 판이 똑같다는 지적에서 나왔다. 확인해 보니 사실이다.

## 지금 무엇이 문제인가 (코드로 확인함)

**라운드 8부터 배치가 한 글자도 안 바뀐다.**

- `computeLaneLayout(수, 속도, 크기)` 는 원숭이 수만 보고 레인을 3마리씩 쪼갠다.
  각도 `±0.09`, 깊이 간격 `6`, 위상은 레인 안에서 균등 분배 — 전부 고정이다.
- 원숭이 수가 `maxMonkeyCount: 10` 에서 멈춘다. 그래서 8라운드에 10마리가 되고
  **그 뒤로는 같은 수, 같은 공식, 같은 좌표다.**
- `allocateMonkeys` 도 규칙이 하나뿐이다 — 구조물 슬롯 4개를 먼저 채우고 나머지가 레인.

**움직임은 축이 하나뿐이다.**

`createPatrol` 이 순수 사인파다. `offsetX = sin(t × 주기 + 위상) × 진폭`.
라운드에 따라 변하는 건 `frequency = 1.8 × 속도` 하나라 **같은 궤적을 더 빨리** 오간다.

**골드는 라운드와 무관하다.**

`settlementGold(점수, 10)` 이고 점수 공식 어디에도 라운드가 없다.
`(100 + 헤드샷 150) × 관통배율 × 연속배율` 이 전부고 연속배율은 2.0 에서 막힌다.
원숭이 수가 10에서 멈추므로 **8라운드나 100라운드나 한 판에 200골드다.**

그런데 체력은 `1 + floor((n-1)/2)` 로 무한히 오른다. 장전 0.8초라 초당 1.25발이
상한이다. 그래서 **시간당 골드가 라운드에 반비례해서 떨어진다** — 높은 라운드일수록 손해다.

## 확정 사항

- **다채로움은 라운드별로 고정이다.** 씨앗이 라운드 번호다. 12라운드는 언제나 같은 판이다.
  라운드 선택 기능과 맞고, 외우면 늘고, 버그 재현과 육안 확인이 가능해진다.
- **네 축을 다 바꾼다** — 움직임 패턴, 대형·배치, 개체별 차이, 구조물 활용.
- **다채로움이 난이도도 올린다.** 체력만 올리는 지금 방식보다 난이도 공식이 풍부해진다.
- 골드 배율은 `1 + (라운드 - 1) × 0.15`.
- 1~3라운드는 지금과 완전히 같게 둔다. 4라운드부터 열린다.

### 뒤집는 결정

직전 인수인계 문서의 **"순찰 궤적(진폭·주기 공식)은 안 바꾼다 — 난이도 균형이 거기
맞춰져 있다"** 가 이 설계로 폐기된다. 사용자가 난이도 상승을 명시적으로 골랐다.
**그 문장을 지우지 말고 정정으로 남길 것** — 조용히 고치면 왜 뒤집혔는지가 안 남는다.

## 1. 골드 배율

```
골드 = floor(라운드점수 / scorePerGold × (1 + (라운드 - 1) × goldRoundMultiplierPerRound))
```

`goldRoundMultiplierPerRound: 0.15` 를 `config.ts` 에 넣는다.

| 라운드 | 배율 | 한 판 골드 (몸통만) |
|---|---|---|
| 1 | 1.00 | 33 |
| 8 | 2.05 | 410 |
| 20 | 3.85 | 770 |
| 50 | 8.35 | 1670 |
| 100 | 15.85 | 3170 |

**나누기와 배율을 한 번에 곱하고 버림은 한 번만 한다.** `settlementGold` 로 버림한 뒤
배율을 곱하면(또는 그 반대) 라운드마다 최대 1골드씩 새고, 낮은 라운드에서 그 비율이 크다.

기준선: 시간당 골드가 평평하려면 배율이 `라운드/8` 이어야 한다 (라운드 50에 6.25).
0.15 는 그보다 위라 높은 라운드가 이득이되 극단적이지 않다.

**초반 반복 파밍은 여전히 막지 않는다.** 다만 이제 높은 라운드가 더 낫다.

## 2. 구성 결정을 한 곳에 모은다

네 축이 전부 "라운드 번호를 받아 무엇을 쓸지 고르는" 문제다. 그래서 결정을 한 군데
순수 모듈에 모으고, 나머지 모듈은 그 결과를 소비만 한다.

새 모듈 `gameplay/roundComposition.ts`:

```ts
export type BehaviorId = 'steady' | 'pause' | 'dash' | 'bob';
export type FormationId = 'columns' | 'wedge' | 'wide' | 'staggered';

export interface MonkeyPlan {
  behavior: BehaviorId;
  speedScale: number;
  sizeScale: number;
}

export interface RoundComposition {
  structureCount: number;
  laneCount: number;
  formation: FormationId;
  monkeys: MonkeyPlan[];   // 길이가 monkeyCount 와 같다
}

export function composeRound(
  roundNumber: number,
  monkeyCount: number,
  structureSlotCount: number,
  config: CompositionConfig
): RoundComposition;
```

**`monkeyAllocation.ts` 가 여기 흡수된다.** 배분도 같은 결정의 일부다. 두 군데서
따로 정하면 "구조물에 셋을 올리는 대형"을 만들 때 서로 안 맞는다.

씨앗은 `createSeededRandom(roundNumber)` 다. `skyMotion.ts` 에 이미 있다.

**`monkeys` 배열의 순서가 슬롯 순서와 같다.** 구조물 슬롯이 앞, 레인이 뒤다 —
지금 `allocateMonkeys` 주석이 말하는 규칙 그대로다.

## 3. 움직임 패턴

`patrolMotion.ts` 의 `createPatrol` 이 `behavior` 를 하나 더 받는다. 반환 모양
(`PatrolSample`) 은 안 바뀐다 — `monkey.ts` 는 곡선이 뭔지 몰라도 된다.

| 이름 | 곡선 | 난이도 가중치 |
|---|---|---|
| `steady` | 지금 사인파 그대로 | 0 |
| `pause` | 양 끝 체류가 김. `sin` 을 끝에서 눌러 평평하게 | -1 |
| `dash` | 느리게 끌다 빠르게 횡단 | +2 |
| `bob` | 좌우 + 위아래 | +2 |

**`steady` 는 지금 곡선과 수치까지 동일해야 한다.** 1~3라운드가 안 바뀌는 근거가 이것이다.

`bob` 만 `PatrolSample` 에 필드가 하나 는다 (`offsetY`). 나머지 셋은 항상 0 을 낸다.
`monkey.ts` 가 그 값을 y 에 더한다.

**도발(`taunt`)은 지금처럼 속도가 0 인 순간에 나온다.** 곡선이 바뀌면 도발 시점도
따라 바뀌는데, 그게 맞다 — 멈추는 순간에 플레이어를 보는 규칙 자체는 유지된다.

## 4. 대형

`computeLaneLayout` 이 `formation` 을 하나 더 받는다.

| 이름 | 모양 |
|---|---|
| `columns` | 지금 그대로. 레인당 3마리, 각도 `±0.09` |
| `wedge` | 가운데가 앞, 바깥쪽 레인이 뒤로 물러난 쐐기 |
| `wide` | 레인 수를 늘리고 각도를 넓힌다. 레인당 인원은 줄어든다 |
| `staggered` | 같은 레인 안에서 깊이를 반 칸씩 엇갈린다 |

**`columns` 는 지금 함수와 좌표가 완전히 같아야 한다.**

제약: 어떤 대형이든 슬롯이 겹치면 안 되고, 화면 밖으로 나가면 안 된다.
지금 각도 한계 `MAX_LANE_ANGLE = 0.09` 가 그 경계다 — `wide` 가 그걸 넘길 때
얼마나 넘길 수 있는지는 육안 확인이 필요하다.

## 5. 개체별 차이

`speedScale` 은 `{0.7, 1.0, 1.4}` 중에서, `sizeScale` 은 소폭으로 뽑는다.
빠른 개체는 작게 — 크기가 난이도 신호가 되어야 플레이어가 우선순위를 고를 수 있다.

**체력은 안 건드린다.** 개체마다 체력이 다르면 점수·정산·마지막 처치 연출과 얽힌다.
별개 문제로 미룬다.

한 판에 같은 종류만 나오면 안 되므로, 구성기가 비율을 정하고 배분한다.

## 6. 구조물 활용

라운드에 따라 구조물 위주 / 레인 위주를 오간다. 지금은 "슬롯을 먼저 다 채우고
레인에 최소 하나" 하나뿐이다. 구성기가 이 비율을 라운드마다 정한다.

**레인에 최소 한 마리는 계속 남긴다.** 지금 규칙이고, 판 전체가 구조물 위에만
서 있으면 통로 하나 무너뜨려 판이 끝난다.

## 7. 점진 해금

전부 한 번에 열면 1라운드가 아수라장이 되고 튜토리얼이 깨진다.

| 라운드 | 열리는 것 |
|---|---|
| 1–3 | `steady` + `columns`. **지금과 완전히 동일** |
| 4+ | 대형 넷 |
| 6+ | `pause`, 개체 속도 차이 |
| 10+ | `dash` |
| 15+ | `bob`, 구조물 편중 |

각 패턴에 위 표의 난이도 가중치를 두고 **한 판의 가중치 합에 상한을 건다.**
안 걸면 `dash` 와 `bob` 만 열 마리가 나오는 판이 생긴다. 상한은 라운드에 따라 완만히 오른다.

## 실패와 경계

- **구성기는 슬롯 수보다 많은 원숭이를 배정하지 않는다.** 구조물 슬롯이 넷이고
  원숭이가 셋인 1라운드가 이미 그 경우다.
- 원숭이 수가 1이면 레인 하나에 한 마리다. `partitionIntoLanes(1)` 이 이미 그렇게 한다.
- **타워 위 원숭이는 진폭이 0이다.** 어떤 behavior 를 배정받아도 안 움직여야 한다 —
  `patrolMotion` 이 이미 `amplitude === 0` 을 특수 처리한다. 새 곡선들도 그 분기를
  타야 한다. 안 그러면 타워 원숭이가 공중에서 흔들린다.

## 검증

| 무엇 | 어떻게 |
|---|---|
| 결정성 | 같은 라운드를 두 번 구성하면 결과가 같다 |
| **초반 회귀** | 1·2·3라운드 구성이 지금 코드와 완전히 동일 |
| 해금 | 해금 라운드 전에는 그 패턴이 안 나온다 |
| 난이도 상한 | 어떤 라운드도 가중치 합이 상한을 안 넘는다 |
| 대형 | 어떤 대형이든 슬롯이 안 겹친다 |
| `steady` 동일성 | 지금 곡선과 수치까지 같다 |
| 골드 | 버림이 한 번만 일어난다. 배율 표의 값이 나온다 |
| 나머지 | **육안 확인은 사용자가 한다** |

전부 순수 모듈이라 단위 테스트가 붙는다. 현재 231개에서 상당히 는다.

## 분할

한 계획서에 넣기에 크다. 넷으로 쪼개고 각각 따로 돌아가는 상태로 끝낸다.

1. **골드 배율** — 작고 독립적. 먼저 나간다
2. **구성 코어 + 대형** — `roundComposition.ts`, `laneLayout` 의 formation
3. **움직임 패턴** — `patrolMotion` 의 behavior, `monkey.ts` 의 `offsetY`
4. **개체 차이 + 구조물 편중**

## 이 설계가 손대지 않는 것

- 개체별 체력
- 점수 공식 (`baseHit`, `headshotBonus`, 배율들)
- `maxMonkeyCount: 10`
- 지는 조건 (여전히 없다)
- 장전 시간, 무기 데미지, 업그레이드 곡선
- 구조물의 물리·붕괴
